# 双机人工/自动窗口与 Agent Team 工作流

版本：1.4 · 2026-09-28。补充 v1.3 的人工接管规则。本文是可复用约定，不是创建团队、启用监听或恢复运行的指令。

## 1. 先固定职责，不按窗口数量增加执行者

延续原有主力机修改、发布机验证的分工。每机指定一个固定执行会话；它可以由用户直接交互，也可以在明确授权下自动推进。所谓“人工窗口”不是只能人工时工作，“自动窗口”也不是第二个部署负责人。

| 入口 | 日常职责 | 默认不得做的事 |
| --- | --- | --- |
| 主力机人工/协调窗口 | 接收用户意图，维护计划，统筹代码实现、回归、团队结果；由指定主力执行会话统一写实现分支 | 直接操作发布环境；把讨论中的方案当部署指令 |
| 主力机自动监听窗口 | 读取获准的 PR/反馈增量，去重，按已授权路径转给固定主力执行会话 | 另起实现团队、修改共享 checkout、自行推进候选或重启部署 |
| 发布机人工/协调窗口 | 核对候选和环境，接受用户接管；由唯一发布执行会话部署、测试、诊断及释放资源 | 跟随最新 head、替主力推共享分支、绕过新实验单 |
| 发布机自动监听窗口 | 识别待接单消息、收集获准的状态、提醒唯一发布执行会话 | 与人工入口各启动一次；因为有新评论就安装/重启/压测 |

若人工/协调窗口就是固定执行会话，可直接工作；若是另一个聊天，只能下达请求，必须交接后才获得写入权。已有两个人工窗口加两个监听窗口可以继续使用，但不能变成四个平级指挥者。

不强制新建四个聊天：已有监听能在固定执行会话内触发时，可减少独立观察窗口。是否合并入口是后续配置事项，本协议不移动、归档或重建现有聊天。

## 2. 三类运行模式

| 模式 | 允许范围 | 适用情况 |
| --- | --- | --- |
| MANUAL | 指定人工/交互会话写入；自动入口暂停或只读 | 临场排查、修改计划、人工修环境 |
| OBSERVE | 自动入口仅观察、去重、通知或按已授权路径转交；固定执行者处理用户已批准任务 | 推荐的日常起点 |
| AUTO_BOUNDED | 固定执行会话在明确的动作、候选/变更范围、资源、时间和次数预算内连续推进 | 用户离开后的有限实验/修复闭环 |

模式按 task 和侧别记录，例如主力 MANUAL、发布 OBSERVE；共享资源和耦合变更仍遵守双端暂停交接。OBSERVE 不授权新的设备检查，读取远端日志也须在既有范围内。自动入口遇到 PAUSED/MANUAL/状态未知时不得派发新动作。

### 自动执行必须有“授权边界单”

在交接单中写明：允许操作、禁止操作、固定候选或允许的候选生成范围、资源 owner、截止时间、最多实验/重试次数、失败分支、发布/推送权限、团队权限和服务释放规则。到期或超出范围就停在安全点并回报。

- 默认允许自动观察，不自动部署新 SHA，不自动创建团队，不自动合并/发布。
- 可明确授权同一服务上的若干检查和失败分支，范围内不必每一小步都再问用户。
- 如需主力自动修复→发布复验的闭环，额外声明“最多几轮、哪些文件/问题可改、哪些本地检查必须通过、能否推送、哪些测试可自动接单”。主力把每个新候选的完整 SHA 和证据登记后，发布机核对并接单；不能用“跟随 latest”代替候选交接。
- 新候选仍由双端确认实际身份；在已明确批准的有界闭环内无需用户重复批准每一步，但扩大问题范围、换基线、换环境大版本、增大负载或暂停后恢复仍需用户决定。
- 核心代码或服务配置改变后，根据影响重建运行身份，不能将旧 run 的结果改名为新候选结果。

## 3. 一次正常协作循环

1. 用户/主力确认目标、验收和授权范围，主力指定 task/计划版本。
2. 主力执行会话组织实现与检查，统一整合可交付候选，发布完整 SHA 和自测证据。
3. 发布执行会话接单：核对协议、计划、实际环境、资源与候选；回复接受/拒绝和 run_id。
4. 发布机按有界实验单执行，各子检查独立编号；保留停止请求与停止服务的不同回执。
5. 发布机报告事实、证据及待证假设；主力组织分析和最小修复。新候选是否自动进入下一轮，取决于授权边界单。
6. 用户可随时查询状态；查询和方案讨论不触发重启。需要写入接管时走暂停/交权；修改了已批准动作后，新计划使旧就绪失效。

两侧负责人通过一个主控制入口交接，监听器只是传递渠道。未授权的跨聊天/跨账号自动发消息不能因为“协作协议”而自行开启；首次采用可由用户分别粘贴同一消息。

## 4. 消息分类与去重

只需七类可读消息，不要求先开发服务端：

- DESIGN：方案或假设，不执行。
- EXECUTE：用户已授权范围内的具体动作，含 command_id、task、epoch、plan_revision、owner、完整候选和边界。
- ACK：已接收/拒绝/安全交权/就绪，分别标明，不能混写。
- RESULT：实际结果与证据，不隐含下一轮授权。
- PAUSE：停止派发，按已有授权收尾并等待交权。
- MANUAL_CHANGE：人工改动与影响记录。
- RESUME：用户确认新版计划后，指定下一步和执行 owner。

每条消息保留 source_event_id 或源链接；转发不生成第二个独立执行命令。去重键至少为 task + control_epoch + command_id；执行者记录 accepted/running/completed/failed/unknown。未知不是失败重试许可，先核对真实进程。

不按“最新一条评论”推断当前指令；核对消息类型、授权来源、supersedes 和明确暂停。晚到的 RESULT 可归档，不能解除后来发出的 PAUSE。冲突时暂停新动作并询问用户。

## 5. 两边都开 Agent Team 的推荐结构

先用每机“1 个负责人 + 2 个按需子代理”，复杂任务再增加；这是工作流建议，不是产品容量保证。实际可用工具和并发上限以各执行会话为准。没有独立子任务时不为了凑队伍而创建团队。

| 所属 | 角色 | 工作产物 | 写入/执行边界 |
| --- | --- | --- | --- |
| 主力机 | 负责人/整合者 | 方案、候选、最终 diff、提交、对外交接 | 唯一共享分支整合/推送者 |
| 主力机 | 代码/契约审查 | 故障假设、调用链、风险与定位证据 | 默认只读，不操作发布环境 |
| 主力机 | 回归测试/独立实现 | 指定测试或模块的补丁、执行记录 | 只写分配目录/隔离工作树；不自行提交共享分支 |
| 发布机 | 负责人/执行者 | 部署、测试、停止/释放回执、独立验证结论 | 唯一共享环境有副作用的执行者 |
| 发布机 | 日志/数值分析 | request/rank/step 关联、首错与反证 | 默认分析归档日志，不登录设备改变状态 |
| 发布机 | 环境/实验审查 | 版本清单差异、启动命令审计、缺失测试 | 默认只读既有材料；实时检查先交执行者统一安排 |

可选的第三个子代理做实现审查或输出/性能分析，但不得顺便成为第二个部署者。工具脚本开发归主力侧统筹，发布侧专注真实环境与证据，减少两边重复写同一探针。

子代理向各自负责人返回结果；跨机正式交接由两位负责人完成。不要让每个子代理都直接指挥对方、各发 PR 评论或自建定时任务。报告有分歧时保留双方证据，用最小区分实验解决，不按多数票判定正确。

### 每个子任务必须明确

task_id、parent/owner、epoch、固定源码/资料版本、具体问题、允许修改的文件、只读/可写权限、禁止资源、输出目录、完成标准、停止条件、时间/资源预算、报告对象。团队启动授权与部署/推送/跨聊天发消息授权分开，不能相互替代。

子代理可能与父会话共享文件系统；角色名不是技术隔离。默认只有负责人执行 git add/commit/push、分支切换和依赖安装。需要并行写同一模块时使用独立工作树/环境，否则串行；共享 Git 元数据、构建目录、缓存和端口仍须协调。

同一 NPU 集群的负载与 profiler 通常串行。只有用户明确批准且确认卡、端口、进程、容器和可变依赖均隔离时才并行不同实验。多代理分析可以并行，不等于多份真实压测可以并行。

团队需要用户明确授权启动，或本任务已有明确团队授权。旧任务曾经开过团队、本文角色表、自动定时触发，均不构成新团队授权。默认不递归创建子团队；需要增加角色时由负责人核对授权和当前资源。

## 6. 暂停、重开窗口与团队生命周期

- 暂停不只通知负责人：停止新的分配，通知全部子代理，在安全点停止写入，登记子进程/构建/部署脚本是否仍在运行，再出安全交权回执。
- 子代理被中断不证明它启动的 shell/服务已经结束；按归属核实。保留 patch、日志、工作区状态，不能 reset/删除用户改动。
- 同一聊天恢复时先读取状态包，核对实际任务是否仍活跃；不能再次创建一套同名团队。
- 重启应用或新开聊天后，不假定旧团队、消息投递和暂停状态已经同步。先确认老执行者及进程状态，再登记新 owner；旧 owner 未交权不能并发接管。
- 不必从头重读整个历史：携带协议提交、当前计划、候选组合、环境摘要、证据索引、未解决问题、旧团队状态及下一步。
- 团队完成后收回写入权，整理结果；不会因下次监听触发自动重生。需要继续工作时明确复用现有子任务或重建并记录。

## 7. 常见冲突及处理

| 冲突 | 处理规则 |
| --- | --- |
| 人工与自动同时下发同一启动 | 同一 command_id，唯一执行者只接受一次；重复提醒仅返回当前状态 |
| 监听窗口自行修代码，人工也在改 | 监听默认只读；写入先转交固定执行者或完成接管 |
| 两个子代理改同一文件或抢 Git index | 负责人划文件范围；冲突文件串行，Git 写操作只由负责人执行 |
| 发布侧临时补丁与主力候选混装 | 补丁单列 SHA/hash，负责人整合后新候选干净复验 |
| 两侧同时压测、抓 profiler 或换包 | 发布唯一执行者排队；资源隔离未证明时不并行 |
| 主力要求新候选，发布仍在旧 run | 新候选排队；当前 run 固定版本，到安全边界再交接 |
| 暂停后子任务/旧定时任务继续 | epoch 失效阻止新动作，并核实在途进程；未知时不宣布交权完成 |
| 两边把假设当结论或互相重复排查 | 主力偏代码契约，发布偏现场证据；统一假设清单，按最小反证实验分工 |
| 自动循环不断重试/消耗 NPU | 明确最多轮次、总时限、资源预算和升级人工条件；未知结果不盲重试 |
| 文档更新后旧自动化仍带历史命令 | 恢复前审阅并替换提示，保存旧版审计，确认新协议和固定角色后才启用 |

## 8. 推荐配置与恢复前的实际工作

初次使用选择 OBSERVE + 固定双执行者。后台无变化保持安静，只通知可行动变化、完成、失败或需要用户决定的事项。监听频率是消息检查频率，不是实验启动频率，更不是实时安全机制；请求超时和紧急止损由实验本地机制与执行者负责。

2026-09-28 只读检查发现，本机 id 为 flashmla 的旧监听状态是 PAUSED，提示中仍保存此前完整实验授权和阶段。它不能只改为 ACTIVE 后盲用；发布机那侧配置本次未读取，不能推定相同。

本次仅提供以下提示模板，不修改真实自动化。正式恢复前应通过支持的自动化管理入口更新已有实例，保留项目/目标会话、频率、模型和通知偏好等无关配置；审阅时保持 PAUSED，用户批准后再启用。不要直接编辑配置文件或新建重复任务。实际工具能否跨账号投递须当场核对，不作自动互通承诺。

### 主力监听提示模板

> 本任务采用工作流 v1.4，固定协议文档提交为……，主控制入口为……，固定主力执行会话为……。只读检查授权范围内的新证据和明确消息，按 task/epoch/command_id 去重。未获得明确恢复、状态冲突或 MANUAL/PAUSED 时不转交执行请求；只按授权保留必要通知。无可行动变化保持安静，有完成、失败或需用户决定的事项才通知。获准转交时保留源消息和同一 command_id；没有跨聊天授权或投递能力时只向用户报告。不得改代码、推送、生成新团队、操作发布环境或自行改写实验计划。不要把历史实验写进长期提示；每次引用当前获准实验单。

### 发布监听提示模板

> 本任务采用工作流 v1.4，固定协议提交为……，主控制入口为……，唯一发布执行会话为……。只识别当前有效 EXECUTE/PAUSE/RESUME 和阶段结果，核对授权、候选及控制轮次；DESIGN/RESULT/普通提醒不触发部署。按同一 command_id 去重，未知在途状态不重试。当前 PAUSED/MANUAL 或缺少恢复授权时不派发。仅按已授权路径通知/转交唯一执行者；不得自行安装、重启、发负载、修环境、创建团队或新建监听。无变化保持安静；资源冲突、异常及需要用户决定时报告。

### 主力团队启动模板

> 我明确授权在本任务主力执行会话启动一个有界 agent team：负责人统一整合；一个子代理只读审查代码/契约，一个子代理在指定测试目录准备回归。先列具体问题、固定 SHA、文件范围、输出和预算，再在授权范围内执行。共享分支提交/推送只由负责人按已有授权操作；不操作发布环境，不新增监听，不递归建队。暂停时包含全部子代理和子进程。当前只允许……；完成条件……。

### 发布团队启动模板

> 我明确授权在本任务发布执行会话启动一个有界 agent team：负责人是唯一部署/设备执行者；两个子代理分别分析归档日志数值、审查环境和实验设计，默认只读不发请求。团队授权本身不解除当前部署暂停，实时设备检查或负载必须有单独有效实验单。跨机结果由负责人统一交接，不抢主力共享分支。当前资料/run……；预算……；完成条件……。

模板只提供以后明确启动的措辞，阅读本页不触发创建团队。

## 9. 后续每个项目如何复用

长期保存协议和模板；新项目只填写任务专用配置：两侧角色/会话、仓库/主控制入口、候选与基线、资源、自动模式与预算、团队授权及实际监听实例。不要把 PR #10 的 SHA、环境、时间窗和历史诊断当新项目默认值。

每次开工先核对 AGENTS.md、任务范围、协议固定提交；只选择适用测试矩阵。主控制入口可为该项目 PR/Issue 或双方约定的版本化状态记录，不再固定用 PR #10。文档版本升级在交接点采用，旧运行保留其原协议和实验身份。

试行指标：重复启动次数、共享写入冲突、过期命令执行次数、失联/未知资源数、无效重启次数、从异常到有效证据的耗时。增加团队人数前先看这些指标是否改善。

## 10. 产品能力与工作约定的区别

官方多代理资料强调：独立、有界的任务适合并行，由主代理汇总；争用同一可变状态或单一慢外部操作时，多代理未必受益且会增加消耗。本页据此优先并行代码/证据分析、串行共享环境操作。[OpenAI 多代理说明](https://developers.openai.com/api/docs/guides/responses-multi-agent)

该来源是 API 文档，用于说明分工原则，不把其 API 开关、并发默认值或生命周期直接套到桌面客户端。桌面当前可用工具、账号权限、自动化和子代理能力须在各会话核对。本工作流没有实现跨机事务、强制权限隔离或自动同步。
