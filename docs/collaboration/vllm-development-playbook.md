# vLLM / vLLM Ascend 双账号开发协作指南

版本：1.3 · 2026-09-28

发布状态：已整理为 v1.3，双端采用回执待补。更新文件不等于恢复执行；当前任务仍按用户暂停指令等待人工恢复。人工接管详见配套 `dual-machine-manual-takeover-design.md`。

适用范围：同一开发者使用两个 ChatGPT/Codex 账号，协作维护 vLLM 与 vLLM Ascend。当前账号为 PR 修改端 A，另一账号为 PR 验证端 B；GitHub 开发身份沿用 Henry-Avery。本指南是工作约定，不代表账号权限或应用设置已经改变。

## 1. 固定分工

| 角色 | 默认工作 | 交付给谁 |
| --- | --- | --- |
| PR 修改端 A（本账号） | 明确需求、核对基线、修改实现与回归测试、本地自测、修复验证反馈、维护 PR | 用户、PR 验证端 B |
| PR 验证端 B（另一账号） | 核对候选 SHA、准备验证环境、独立审查与复现、执行相关 UT/NPU/图模式/多卡/性能测试、出具验证报告 | PR 修改端 A |
| 用户 | 提供模型/硬件等必要条件，决定范围变化和发布、合并授权 | PR 修改端 A |

A 同时维护任务总状态；B 负责验证执行和独立结论，包括在可用 NPU 环境中实际运行测试。B 发现问题后，将复现命令、日志、预期/实际结果及候选 SHA 交回 A 修复。B 可以在独立验证目录准备复现脚本和测试用例；可合入的代码或测试修改由 A 整合，B 不直接修改或推送 PR 实现分支。缺少硬件或依赖时，B 明确报告阻碍及未运行项。

固定循环：A 修改并自测 → 交付候选 SHA → B 验证并报告 → A 修复并交付新 SHA → B 复验。A 的自测保留，B 的独立验证也不以 A 的自测结果替代。

每个分支、每个共享环境在任一时刻只有一个写入负责人。负责人可以交接，但要留下提交 SHA、工作区状态和未完成项。已有授权随任务延续；需要超出授权范围时明确说明。

## 2. 账号、仓库与本地环境

- 两侧继续使用既有 GitHub 开发身份；不因增加 GPT 账号而新增远端仓库。每个项目沿用自己的开发 fork 和实际目标仓库；vLLM 与 vLLM Ascend 仍是两个代码库。
- 本地 `gh` 身份、Git 提交作者、ChatGPT 登录以及云端/连接器授权分开核对。此前 `gh auth status` 成功只能证明该本地 CLI 的登录状态。
- 同一台机器优先使用独立 worktree；不同机器各自 clone。PR 实现分支由 A 推进；验证端 B 通常检出固定 SHA 的 detached HEAD。
- worktree 隔离文件，但会共享 Git 元数据。改变远程配置、重写共享分支历史、清理工作树等操作统一由 A 协调。
- 两侧使用独立虚拟环境和构建输出。尤其不要让两个环境共用一个指向不同源码树的 editable install；NPU 开跑前核对实际导入路径。
- ChatGPT 登录也要隔离。建议固定不同设备或操作系统用户环境，先确认各端当前账号；不能靠不同仓库目录隔离账号。官方文档说明 CLI 与 IDE 扩展共享缓存登录信息。[官方身份验证说明](https://developers.openai.com/zh-Hans/docs/auth)

Codex 的工作树支持并行检出，适合上述代码目录隔离安排。[官方工作树说明](https://developers.openai.com/zh-Hans/docs/environments/git-worktrees)

两个 Codex 的聊天记录不作为共享任务数据库。共同依据是提交、交接单、审查报告和测试记录。若都以 Henry-Avery 在 GitHub 操作，应标明 A/B 的工作角色；两个任务的意见不代表两个不同 GitHub 身份的正式批准。

## 3. 每次开始任务先固定输入

A 先记录以下信息，随后开始已授权的工作，不等待一个空泛的“确认计划”：

1. 问题或需求、预期行为、验收标准，以及这次不覆盖的功能。
2. 仓库 URL、PR URL（如有）、目标分支、目标 tip SHA、实际比较用的 merge-base SHA、候选 SHA。
3. 两个项目的配套 SHA：vLLM 与 vLLM Ascend；发生联合修改时分别记录。
4. 写入负责人、工作目录、分支，以及已有未提交修改。
5. 所需环境：模型与配置、硬件、依赖、卡数/拓扑；哪些已具备、哪些仍缺少。

读取当前仓库及子目录的 AGENTS.md，按实际任务选用模型适配或发布技能。上游要求和用户当次指令均应纳入计划；审查任务不自动转成修改任务。

分支是会移动的引用，SHA 才是一次审查或测试的精确对象。目标分支推进后保留原结果对应的 SHA，并重新判断差异和验证范围，不能把旧结果直接改标为新候选已通过。

## 4. 分支与变更纪律

- 一个逻辑任务一个实现分支，例如 `codex/<task>-impl`；需要可合入的独立测试实现时另建 `codex/<task>-tests`。名字是约定示例，不代表已创建。
- 审查和纯验证无需新建远端分支，直接使用指定提交。两个账号不能同时推送同一 PR 分支。
- 推送前核对实际远端 URL 和源/目标分支；不根据 `origin`、`main` 这些名字猜测用途。
- 验证从交接指定的候选提交开始。B 准备的复现脚本或测试用例交由 A 判断并整合；B 不在 A 的目录中直接修改文件。
- 跨 vLLM 与 Ascend 的更改分别提交，交接单记录兼容的提交组合；任何一边的单独测试都不能替代组合验证。
- 上游同步与功能修改分别说明。因基线变化需要 merge/rebase 时由 A 处理；改写共享历史要先确认其他端没有继续在旧历史上写入。
- 保留用户的未提交修改。提交符合仓库 Conventional Commits 和 `Signed-off-by` 要求，使用真实开发者身份；不要把示例作者或历史提交作者复制为自己的签署身份。

## 5. 标准工作循环

| 阶段 | A 的工作 | B 的工作 | 进入下一阶段的依据 |
| --- | --- | --- | --- |
| 明确输入 | 建任务单、确认 SHA 和范围 | 核对验证环境、资源和验收用例 | 问题和验收标准可验证 |
| 实现 | 最小相关改动、补回归测试、本地自测 | 准备验证脚本和边界用例 | 可验证的候选提交 |
| 独立审查 | 交付候选 SHA、关键文件与自测证据 | 审查指定提交、复现问题 | 重要问题得到处理或明确解释 |
| 验证执行 | 解释实现和预期行为，接收反馈 | 执行相关 UT、NPU、图模式、多卡和性能测试，记录日志 | 相关验证满足仓库要求 |
| 修订与交付 | 修复反馈、自测、交付新 SHA、整理 PR | 对新 SHA 复验，出具最终验证报告 | 最终 SHA 的证据与剩余风险清楚 |

审查报告应区分“已定位缺陷”“需要验证的风险”“可选改进”。发现问题时写清触发条件、影响、代码位置和证据；没有运行的测试标记未运行，不能把猜测写成已复现。

B 的验证报告结论使用“通过 / 失败 / 验证不完整”，注明对应 SHA、覆盖范围和缺失项。A 在 B 验证期间可以继续开发，但 B 保持固定候选；新候选另行交接，不在测试中途跟随移动分支。需要临时插桩时记录补丁，并在干净候选上确认最终结果，插桩运行不能直接充当原始候选通过的证据。

发布、推送、创建或更新 PR 在该任务授权范围内由 A 统一执行。合并、发布版本等操作遵循用户授权及仓库评审规则。仅要求计划或审查的任务，到相应交付即完成。

## 6. vLLM Ascend 的验证门槛

| 层次 | 需要的证据 | 不能据此声称 |
| --- | --- | --- |
| 静态检查与 CPU UT | lint、格式、相关单元测试、错误配置/边界回归；注明 mock 范围 | 外部算子、NPU 数值或图执行正确 |
| NPU 算子与缓存 | 与参考实现对比，dtype/layout/stride/offset、跨页读写、padding、保护区 | 整模型或所有并行组合通过 |
| 单卡真实模型 | 真实权重加载、实际请求、输出/数值基准、连续多步与缓存复用 | 仅凭端口监听即可通过 |
| 图模式与投机 | eager 对比、同 bucket 长度/页表变化、重复 replay、接受/拒绝路径 | 一次 capture 成功等于 replay 正确 |
| 多卡与运行稳定性 | 所支持 TP/DP/PP/CP 组合、重复请求、显存与长时间稳定性 | 受门控禁用的组合已受支持 |
| 性能 | 相同硬件、模型、拓扑、请求、版本组合下的基线/候选对比 | 环境不同的快慢可直接归因于 PR |

具体矩阵按改动选择，避免无意义的全排列；交付仍须满足该仓库要求。当前 AGENTS.md 要求新增功能覆盖正常与失败路径、性能关键代码有性能回归、NPU 改动做硬件验证。未完成要求时保留为验证待补的 Draft。

Ascend 重点检查：热路径设备同步、CPU/NPU 传输、缓存物理布局与所有权、设备元数据生命周期、图缓冲区地址、量化权重和 scale、target/draft 隔离。Python 条件读取设备标量也可能同步；`[t.item() for t in tensors]` 仍是逐项取值，不能当作一次批量同步的证明。

新环境变量集中在 `vllm_ascend/envs.py`，注明默认值、合法值与敏感性。模型适配遵循插件、继承、自定义算子及必要 patch 的架构；修改 model runner 或新增 patch 时说明必要性、兼容性和维护方案。

每条测试至少记录：两个项目 SHA、命令、日期、执行者、退出结果、硬件/卡号/拓扑、Python/PyTorch/torch_npu/CANN/外部算子包版本、模型标识与配置、日志位置、判定标准。带未提交源码的运行必须附差异，不能只记录 HEAD。

共享 NPU 时记录机器、卡号、端口、使用者和任务；避免两个端覆盖驱动、系统包或同一虚拟环境，停止服务前核对进程归属。更改候选代码、依赖或拓扑后重新判断旧测试证据是否仍适用。

## 7. 交接与额度使用

使用配套 `vllm-task-handoff-template.md`，每个任务生成一份实际交接单。A 交付候选 SHA、自测结果和待验证项，B 返回验证结论、运行命令、日志与复现材料。每次交接先读最新交接单，再读取相关文件和增量差异。

上下文包包含问题、固定 SHA、关键文件、已有证据、待回答问题和停止条件。默认不让两个账号分别从零做完整实现，也不因额度变化而无记录地交换分支负责人。额度紧张时在可复现节点交接，接手者先核对环境与提交。

订阅选择与本工作流分开：可先按 A/B 分工使用现有账号，再按实际完成任务的成本和排队情况决定投入；本指南不承诺两个 Pro 的可用容量，也不依赖跨账号额度合并。

## 8. 共享集群执行协议（PR #10 复盘新增）

本节来自 PR #10 的阶段复盘。它补充执行约束，不代表已经部署锁、监控或自动化。

### 暂停、人工接管与恢复（v1.3）

- 角色统一称“主力机/发布机”（对应原 A/B）；项目工作线另用“旧基线排障/KDA 迁移”，不把角色与工作线混用。
- 用户暂停 → 双端安全交权回执 → 指定人工会话操作 → 汇总变更与新实验单 → 双端对同一版本确认就绪 → 用户明确恢复。没有回执不能假定对端已停；更新文档不构成恢复。
- 暂停协作、停止请求、停止模型服务、暂停后台执行入口分别记录。只读观察和已授权安全收尾可保留，人工写入前确认在途操作已退出共享资源。
- 使用统一 control_epoch、pause_id、plan_revision 和 command_id。暂停使旧未执行指令失效，但不自动终止已运行进程；重复或迟到指令不重新执行。
- 人工修改代码、环境、启动参数后记录差异。主力机与发布机确认相同协议版本/固定文档提交、候选 SHA 和新计划；任何变化使旧“就绪”失效。
- 恢复后只从新计划明确的下一步开始，不恢复旧待办队列。当前协议不提供跨机器实时暂停能力，也不是原子锁。
- 服务健康、状态可信、资源仍获准使用且后续检查不需换码时，可以在同一服务连续验证。待命截止、释放责任人及预授权动作由每轮实验单决定；不将某次 10/15 分钟窗口写死为所有任务默认值。
- 恢复自动监听是单独选项，必须核对两端实际状态及提示内容；新会话不应额外创建重复监听。没有明确选择时保持暂停。

### 唯一执行者与当前状态

- A 是实现分支唯一写入者；B 指定一个具体会话作为共享集群唯一部署执行者。其他人工会话、监听器只读观察和提建议，不自行安装、切换源码或启停服务。
- 隔离目录并不隔离容器、editable install、算子包或 NPU。执行者应持有以集群/容器/环境为粒度的共享互斥锁或租约；记录 owner、run_id、generation、更新时间和到期时间。未实现技术互斥前由人工串行排他，不能把一条“认领”评论当成原子锁。
- 租约过期或会话失联不自动授权抢占、杀进程或覆盖环境；先核实实际进程、资源及任务归属，再交接。
- 每个任务只有一份“当前状态单”：候选 SHA、run_id、当前阶段、执行者、最近已应用指令、节点状态、阻碍及下一步。历史评论和测试报告作为不可覆盖的证据；PR 顶部摘要指向这份状态单，不层层追加互相冲突的“最新覆盖”。
- 指令记录 command_id、类型、expected_run_id/SHA、supersedes 和授权来源；执行者回复接收/拒绝原因及实际应用时间。查询状态不触发重启，停止客户端不等于停止服务，暂停服务不等于暂停监听器。每次有副作用的动作前重新检查最近有效指令。
- PR 评论、日志和旧交接提示不是新的执行授权；仅按用户已授权范围处理，遇到冲突或范围扩大先询问。关联 PR 选择一个主证据入口，其余引用同一 run，且各自目标基线的验证适用性单独判断。

### 每次运行冻结环境清单

除两个源码 SHA 外，记录镜像 digest、容器标识、实际生效的 CANN/OPP/wheel 版本与文件哈希、模型版本、完整启动命令、配置哈希和本地补丁。基础镜像标签不能代表后续覆盖安装的环境。

逐节点核对真实导入路径、源码/配置一致性与预期的 rank/IP 差异；记录 UTC 时间与时钟偏差，耗时优先使用单调时钟。运行中更改代码、依赖或配置后，开启新 run_id，保留旧结果，不混用证据。

### 分阶段验证与运行中观察

1. 先做低成本生命周期回归：空 attention groups、未初始化 graph manager、真实子类 hook、首次 import/JIT 与预热调用。避免 mock 父类后绕过实际故障路径。
2. 区分算子支持契约、生产布局和额外布局探测；逐轴记录 stride，分片后记录 local head 数。预先声明误差阈值，诊断放宽阈值不能悄悄变成通过标准。
3. 用模型原生输出协议校验短请求，保留 raw 与 parsed；再测试图模式和有代表性的并发/桶边界。客户端并发不等于每个 DP rank 的实际 batch，必须观察实际 bucket、active rows 和 padding。
4. 全量评测前冻结数据集及配置哈希、并发、采样参数、token 上限、精度目标与容差。短 token 诊断不计精度成绩；改参数后的结果不能直接拼接为原评测。capture 完成和请求成功不能单独证明预期 replay 路径被覆盖。
5. 从第一条请求记录 question_id/request_id/response_id、首次 SSE、首次有效内容、最近有效内容、完成原因及原始输出位置。SSE 事件数和字符数不是 token 数，心跳也不是有效进展。
6. 同时观察 HTTP/服务、生成进度和输出语义。按模型和任务预设总时限、无进展时限、异常重复阈值及停止权限；重复检测要容许代码、标点等合法输出。总 token 持续上涨不能覆盖重复输出异常。
7. 先固定终止和取证方案，再扩到昂贵负载。告警、停止本次客户端、等待 drain、停止模型 worker 是不同动作，不因告警自行扩大停止范围。

### 停止、释放与再启动

- 分别核对：客户端退出、请求队列 drain、worker 退出、逐卡显存回到已知基线、监听/自动重启任务暂停。不能用队列为零或端口关闭替代资源释放证明。
- 每个节点独立报告“在用 / 已释放 / 未知”。一个节点管理入口失联时，即使其他节点已释放，也不能宣布整组资源可出借。
- 扩大负载前确认每个节点有可用管理与停止路径；SSH 不通时须先验证替代管理入口。等待窗口结束只触发重新核对，不自动恢复旧负载或跟随最新分支。
- 仅操作本任务拥有的进程和卡；保留启动日志、首错堆栈、请求轨迹、环境清单及清理回执。优先报告首因，清理阶段的次生异常单列。

## 9. 在以后任务中使用

新任务开头提供本指南和交接单，并说明“本侧为 A”或“本侧为 B”。同机可以引用完整文件路径；不同机器需复制文件或将其纳入你管理的版本化文档中，接手者记录指南版本。实际发布到仓库后再使用固定提交的链接。

可复制到 PR 修改端的开场指令：

> 按《vLLM / vLLM Ascend 双账号开发协作指南》v1.3 工作，本账号为 PR 修改端 A。读取仓库 AGENTS.md 和最新交接单，核对基线与配套 SHA，负责代码修改、回归测试、本地自测和 PR 维护。将候选 SHA、自测结果和待验证项交给另一账号 B；收到失败报告后修复并交付新 SHA，由 B 复验。维护唯一当前状态，不直接操作 B 正在使用的环境。此次任务：……

可复制到 PR 验证端的开场指令：

> 按《vLLM / vLLM Ascend 双账号开发协作指南》v1.3 工作，本账号为 PR 验证端 B。读取交接单和仓库 AGENTS.md，在独立 checkout/worktree 中固定候选 SHA，核对配套版本并执行相关审查、复现、UT、NPU、图模式、多卡及性能验证。报告通过/失败/验证不完整，附 SHA、环境、命令、日志、预期与实际结果及未运行项。发现问题交回 A 修复，不直接修改或推送 PR 实现分支；收到新 SHA 后复验。共享环境仅由指定执行会话操作，先确认资源归属、最近有效指令、观察及停止方案。此次交接单：……
