# 双机协作：暂停、人工接管与恢复协议

版本：1.4 · 2026-09-28（与协作指南统一编号）

状态：用户已要求趁暂停窗口更新协作文件；本协议纳入 v1.4，双端采用回执待补。文件更新不代表任一会话、监听器、服务或定时任务已经采用新协议，更不构成恢复。以实际暂停回执为准，恢复前完成本协议的双端核对。

## 1. 目标与角色

适用于主力机与发布机正在协作时，用户需要分别进入两边人工排查、修改代码或调整指令，然后让双方继续协作的情况。

- 用户：决定暂停范围、人工操作人及恢复的计划。
- 主力机：平时负责实现分支；接管时报告代码、命令和未完成写入状态。
- 发布机：平时负责部署环境；接管时报告运行、请求、服务与资源状态。
- 人工执行会话：用户直接操作终端，或用户指定的交互会话。接管后可在授权范围操作；不是让所有会话都停到无法交流。
- 后台监听/其他会话：接管期间只读，不派发新任务、不推送、不安装、不启动请求、不启停服务。只读监听与原已授权的安全止损可以保留，须列明。

角色使用“主力机/发布机”，项目工作线另用“旧基线排障/KDA 迁移”等名称，避免两个维度都叫 A/B。

核心约束：同一目录、分支、容器或服务在任一时刻只有一个写入执行者；所有权必须先交出，再接管。修改聊天指令或新增 PR 评论本身不证明旧执行已经停止。

## 2. 三种动作要分开

| 动作 | 含义 | 是否停止模型服务 |
| --- | --- | --- |
| 暂停协作 | 禁止旧计划继续派发和执行新动作，处理已在途操作 | 不自动停止 |
| 人工接管 | 已确认安全交接，指定人/交互会话获得明确范围的写入权 | 依接管单决定 |
| 停止并释放 | 停止本任务请求与 worker，逐节点确认资源释放 | 是，必须单独授权或符合既定止损规则 |

暂停请求必须选择在途请求策略：取消并排空，或仅允许已提交请求在原止损/时限内结束；未选择时，先阻止新动作并回报在途状态，不擅自杀服务或声称已排空。后台客户端仍持续提交请求时，不能算“只有在途请求”。

服务策略另选：保留待命至指定截止时间，或释放。待命须有资源使用授权和可信服务状态；有污染/设备故障疑点时，不把保留的服务用于精度验收。截止后的释放只能由接管单指定的当前资源 owner 按预授权执行，不唤醒已交权的旧执行者。

## 3. 最小状态流

正常协作 → 暂停中 → 人工接管 → 待恢复确认 → 正常协作（新轮次）

| 状态 | 允许做什么 | 进入下一状态的条件 |
| --- | --- | --- |
| 正常协作 | 只执行当前已批准实验单 | 用户发出带范围的暂停请求 |
| 暂停中 | 不派发新动作；当前 owner 收尾/取消在途操作并保存证据 | 所有受影响端确认已安全交权 |
| 人工接管 | 指定人工会话按范围修改；其余只读 | 人工变更已汇总，提出新计划 |
| 待恢复确认 | 主力机与发布机只做核对，不启动部署或请求 | 两端对同一计划确认就绪，用户明确恢复 |
| 正常协作（新轮次） | 新 owner 执行新计划第一步 | 旧待办保持作废，不补跑旧队列 |

只有一端确认暂停，另一端应标“未确认”，整体仍是暂停中。超时、失联或聊天停止输出均不等于成功交权。

默认暂停影响当前任务的双端协作；确实仅单侧只读查看日志时无需全局接管。单侧写入接管只有在资源完全隔离、另一侧仍固定运行版本且不会读取变化时才可采用，并写清边界。

## 4. 暂停与交权：两端都要回执

用户发布同一份暂停单，包含 task、control_epoch（控制轮次）、pause_id、影响范围、在途请求策略、服务策略和指定人工 owner。单一控制记录维护者负责递增 epoch；两边不各自发号。新暂停使旧轮次未执行命令失效，但不会自动取消已经在运行的进程。

主力机暂停回执至少包含：

- 当前 HEAD、分支、工作目录、未提交差异与归属。
- 在途编辑、构建、提交、推送是否已结束；有子任务或子进程写文件时一起核对。
- 后台执行入口是否已暂停/进入只读，以及未派发队列已标失效。
- 已交出的目录/分支写入权、允许人工开始的位置、证据时间。

发布机暂停回执至少包含：

- 当前实际 SHA、run_id、容器/环境/节点、部署执行者。
- 请求提交器是否停止，running/waiting 是否排空；若保留在途请求，明确哪些资源尚不能接管。
- 安装、同步、启动、停止脚本是否仍在途；各节点管理入口是否可达。
- 服务状态、资源归属、保留截止时间或释放证据；后台自动重启/执行入口状态。
- 已交出的环境/服务操作权、仍未知的部分。

“收到暂停”是接收回执，不是安全交权回执。只有双方受影响范围都达到安全点，用户或指定协调者才能宣布进入人工接管。正在推送、安装等不宜强杀的操作，先报告并在安全边界结束；用户明确紧急停止时优先按授权范围处理，事后仍须核实实际状态。

## 5. 人工期间如何两边分别工作

- 主力机人工会话可修改指定代码/测试/实验设计；发布机人工会话可按授权检查或调整现场。两者可以并行，但不能同时写同一资源。
- 修改主力机候选不要求发布机立即安装；禁止在服务运行时覆盖它依赖的源码、包或 editable install。换代码/包/启动配置需要单独部署与必要重启。
- 发布机若临时改源码，在独立目录/补丁分支记录 patch 与原 SHA，由主力机整合；除非另行交接，发布机不写共享实现分支。
- 改动及时记入接管记录：旧值→新值、文件/commit/patch、环境和启动命令差异、执行者、时间、影响的证据。
- 人工口头讨论先记为设计；明确标记“执行”且在用户授权范围内的动作才可实施。旧自动化提示词、新聊天建议、历史 PR 评论不得绕过接管状态。
- 停止人工操作前交回所有权；不能在自动执行恢复后继续在同一环境手改。

## 6. 恢复：先准备，后明确执行

### 第一步：汇总并提出恢复单

主力机汇总人工改动，给出完整候选 SHA、配套版本、新 plan_revision、下一步实验及分支条件。发布机补齐实际环境、依赖/补丁、资源占用及是否必须重启。没有代码变化也要更新控制轮次，避免旧指令重放。

恢复单必须包含同一服务可连续执行的检查、异常时停止请求还是停止服务、何时释放、哪些结果不再适用。诊断版本与干净候选分开，不能把人工插桩结果当原版本验收。

### 第二步：双端准备回执

两边均回复同一 control_epoch、plan_revision、候选 SHA 和下一步动作“就绪”。就绪只表示可执行，不启动服务、不推送、不发测试请求。若任一端随后修改了计划或实际环境，旧就绪失效，重新确认。

### 第三步：用户明确恢复

用户确认“按这份恢复单继续”，或在明确的先前授权内由指定协调者确认；本协议默认由用户确认。恢复记录指明新执行 owner 和新 command_id。两端先确认自己已让出人工写入权，再恢复各自执行入口。

协议采用回执还必须包含版本号与固定文档提交/哈希；仅口头说“已读最新版”不足以确认一致。是否恢复原有自动监听由用户单独选择；没有选择就保持暂停，不能因恢复一项人工实验就自动恢复全部后台工作。

旧排队任务全部标为 superseded，保留审计记录而非删除；旧进程不能仅凭新 epoch 假定已退出。过期命令、重复命令不重新执行；已启动但结果未知的命令先核实实际状态，不直接重试。正常自动执行只从恢复单列出的下一步开始，不从暂停前队列断点盲目续跑。

需要换版本、环境或负载计划时开新 run_id，并链接上一轮；仅暂停沟通且实际运行完全未变时，可保留原服务实例 ID，但新的实验仍使用独立 experiment_id。

## 7. 通信与当前状态：先采用轻量方式

不新建第二套调度系统。沿用任务现有主证据入口，维护一份小型控制记录，暂停、回执、变更和恢复用带 ID 的追加记录。当前摘要指向这些记录，只由指定协调者更新；其他人追加自己的回执，不互相覆盖。

建议控制摘要字段：

```yaml
# 示意字段，不是可执行配置，也不表示当前真实状态
task: example-task
control_epoch: 7
state: MANUAL
pause_id: pause-007
plan_revision: plan-003
coordinator: user-designated-session
main_owner: named-manual-session
deploy_owner: named-manual-session
candidate_sha: full-sha-to-be-filled
run_id: existing-run-or-none
main_ack: safe-to-handoff
deploy_ack: safe-to-handoff
service_policy: keep-until-explicit-deadline
service_deadline_utc: to-be-filled
next_action: none-until-resume
resume_authorization: none
```

首次试行时，用户把同一暂停单分别交给两边，收到双回执后才接管；恢复同理。以后若启用已有授权的消息转发，可减少重复粘贴，但转发成功不等于暂停成功。发给单边的消息不会天然同步到另一台机器。

PR 评论/状态文件只是记录，不是原子锁；同一 GitHub 身份也无法证明来自哪个执行会话，因此必须写角色和会话标识。未实现技术门控前靠人工排他，不能宣称能强制阻止失控脚本。

若以后自动化：所有有副作用的入口都须检查当前控制轮次、模式、计划版本和 owner；读取失败或状态冲突时拒绝新动作，仅保留既有授权安全收尾。要获得强互斥，还需执行端锁/串行执行器与旧 owner 隔离，单纯“检查后执行”仍存在竞态。此实现应另行评审，不在当前故障排查中插入。

## 8. 可复制的人工指令

### 暂停单

> 【暂停协作｜task=…｜epoch=…｜pause_id=…】主力机和发布机暂停旧计划的新动作，后台执行入口暂停或只读；不等于停止模型服务。在途请求策略：……；服务保留/释放策略与截止时间：……。分别回报实际 SHA、在途操作、工作区/资源状态及安全交权结果。双方完成交权后，由主力机人工会话……和发布机人工会话……分别接管……范围。未确认前不进入共享资源人工写入。

### 人工修改完成

> 【人工交回｜pause_id=…】主力机改动：……；发布机改动：……；最终源码/环境/补丁：……；未完成项：……；人工写入已停止。建议恢复单 plan=…，下一步……。请两端核对，只回“就绪/阻碍”，暂不执行。

### 恢复单

> 【恢复协作｜task=…｜epoch=…｜plan=…】两端已确认同一候选和计划，人工写入权已交回。批准从……开始，主力机执行者……，发布机唯一执行者……；资源、止损和服务保留规则按本恢复单。旧轮次未执行指令全部失效，不重放旧队列。先回报已采用的新状态，再按本单执行。

## 9. 异常情况与试行验收

- 一侧失联：另一侧停止新协作动作，保留现场；未确认范围不可接管或宣称已释放。需要实际管理入口核实后才能转移控制权。
- 人工期间旧任务醒来：应识别 MANUAL 状态并只读退出。若实际仍写入，暂停接管操作、记录碰撞并由资源 owner 处理，不能继续假定隔离成立。
- 用户再次发暂停/变更：使正在准备的恢复单失效；停止派发，已在途动作重新核对。恢复需要对新版计划确认。
- 重复收到恢复消息：按 command_id 核实已应用状态，不重复启动服务或请求。
- 两侧都说就绪，但 SHA/plan_revision 不一致：拒绝恢复，先对齐。
- 服务待命到期：按接管单预授权由当前 owner 释放并回执；没有预授权则请用户决定，不擅自占用到无限期，也不擅自杀服务。

下一轮先采用一次“暂停→双回执→小范围修改→双就绪→恢复”。验收关注：暂停后有无新副作用、同一资源是否出现双 owner、旧指令是否被重放、版本是否一致、服务是否不必要重启、未知资源是否被误报释放。v1.4 已纳入简版规则；更复杂的锁与转发实现待试行验证后单独设计。
